## Findings

- **[severity: fragile]** DESCRIPTION:32 (`crate (>= 0.12.0)`) — the floor does not check for the capability knowledge needs. crate's `main` is now at 0.12.1 (Release v0.12.1, 301c158), and its `crt_receipt_write()` has no `file =` argument (`git show origin/main:R/crt_receipt_write.R`, line 80). `file =` exists only on the `47-receipt-file-name` branch, which is at 0.12.0. So a machine with crate 0.12.1 from main passes the floor: `pkgload::load_all()` loads it without complaint. 0320 then fails with "unused argument (file = ...)" at `knw_grade_receipt_write()`. That call comes after the first key's grade table and record have been written, so a full retune stops after its first grading, and the database host is where this would happen (task_plan line 111). 0325 is not affected, because `knw_publish()` uses crate's default file name. Two ways to fix it while crate is unreleased: check `"file" %in% names(formals(crate::crt_receipt_write))` at 0320's start, before any scoring or grading; or make the floor a version that only the branch carries (e.g. 0.12.1.9000 on the branch). The plan's open box (raise the floor to the release that ships `file =`) closes it once that release exists.
  - **Rule:** code-check-shell.md "Assert capabilities, not versions — a tool upgrade can remove one silently"

- **[severity: bug]** scripts/0320-tune-run.R:621-631 (the keep path) — a kept table with no matching receipt gets one written now, saying the current run made it. The receipt's `recipe.code` takes `knowledge_git`, this pass's full commit and dirty flag, read at this run's start. But the table was graded by an earlier pass, and the kept record (`write_record` runs only when the record is missing) still names that earlier pass's `knowledge_commit`. The keep check compares the rule, run, walk, flow load, prior, gate, evidence and gradient; it never compares the code. So a candidate resumed with `RUN=` after a code change produces a receipt and a record for the same table that name different commits. The receipt's `recipe_id`, the identity a rebuild is compared against, then claims a recipe that never made the table. The first resume of a pre-receipt candidate after this merges hits it for every kept key. Fix: compare the record's `knowledge_commit` with `knowledge_git` (short-SHA prefix plus `+dirty`) and regrade when they differ. Or write the receipt from the commit the record names, resolved to its full SHA with `git rev-parse`, and refuse when it cannot be resolved or the record says `+dirty`.
  - **Rule:** code-check.md "Written data outlives the fix"

- **[severity: fragile]** R/receipt.R:33-37 (`.knw_git_state()`) — `dirty` treats a failed `git status` as a clean tree. `system2(..., stdout = TRUE, stderr = FALSE)` does not raise on a non-zero exit: it returns whatever was printed to stdout, with a `status` attribute. Here stderr is discarded and the status is never read, so a failing `git status -- R scripts inst` yields `character(0)` and `dirty = FALSE`. That value is written into every grade receipt's `recipe.code` and into `recipe_id`. The commit lookup above it does refuse, but only on its own output. Fix: read `attr(out, "status")` on the status call and stop when it is set.
  - **Rule:** code-check-r.md "`system2(stdout = TRUE)` warns on a non-zero exit instead of raising, so a `tryCatch(error =)` around it never fires" ; code-check.md "A guard that fails toward pass"
