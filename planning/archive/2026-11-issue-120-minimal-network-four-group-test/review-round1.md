- **[severity: bug]** scripts/0320-tune-run.R:187 — The branch changes the first log line from `Evidence build %s on link run %s …` to `Evidence build %s (%s) on link run %s …`. `data-raw/vignette_chinook.R:91` parses that line with `sub("^.*Evidence build (\\S+) on link run.*$", "\\1", log1)` to find the run's evidence ledger. After the change the pattern no longer matches, because ` (<evidence_dir>)` now sits between the path and ` on link run`. The script then stops at line 92 with "the tuning log's first line names no evidence ledger on disk". I reproduced this on this branch's own log: `scripts/logs/habitat/minimal_network_120/20261102_tune_run-20261102_173001-p20261102171045-bt.txt` gives `identical(sub(...), line) == TRUE`, so nothing is extracted. `scripts/0335-promote.R:160` reruns `data-raw/vignette_chinook.R` after every promotion. So the next promotion of any candidate graded by this 0320 fails at the chinook bundle, after the tables have already moved. (`scripts/0322` uses the same regex but is pinned to a 2026-10-17 log, so it is not affected.) Fix: keep the old shape, with the path immediately before ` on link run` and the directory after it, or update the reader's regex in the same commit.

- **[severity: fragile]** R/tune_promote.R:86-95 (and the claims in CLAUDE.md, the 0320 header and scripts/README) — The floors guard checks only the main summaries (`cand[[k]]`). `knw_tune_promote()` also promotes the candidate's `grad_fwa/` summaries (lines 182-191 and 260-261), but reads only `evidence_md5` and `run_uid` from them. Nothing in 0320 holds a `GRADIENT=fwa_gradient RUN=<run>` sensitivity pass to the main run's `MIN_WSG`/`FOLDS`. So a sensitivity scored with `MIN_WSG=4 FOLDS=4` into a default-floor candidate is promoted into the tracked `data/tune/grad_fwa/`, which `data-raw/vignette_method.R` reads for the methodology article's sensitivity sentence. CLAUDE.md says "each summary records them and `knw_tune_promote()` refuses any other"; for the `grad_fwa/` summaries that is not true. Fix: apply the same floor check to `fwa_cand[intersect(keys, names(fwa_cand))]`.
  - **Rule:** code-check.md "A guard's scope, escape hatches, and remedies"

- **[severity: fragile]** R/parent_join.R:12-15 (man/knw_parent_join.Rd details) — The roxygen says "where a full segment straddles a minimal break, `straddle_m` is the length that lies on another minimal segment, so a visit on that stretch reads the other segment's gradient." As a statement of what this function returns, the code contradicts it: `knw_parent_join()` gives every visit on the full segment the main parent's `gradient_minimal`, wherever the visit sits on the segment, and only carries `straddle_m` along. A visit on the straddling stretch reads the other segment's gradient only on the minimal network itself. That is the sense `data-raw/minimal_network_check.R`'s header uses ("which read the other minimal segment's gradient on part of their segment"). A reader of the exported function's documentation would take it that the join assigns the other gradient there. Reword it as a consequence on the minimal network, for example "so on the minimal network a visit on that stretch reads the other segment's gradient, not the parent's".
